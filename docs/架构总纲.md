# 身份卡 · 架构总纲

> 回答「为什么这么设计」。改动前读它，改完同步它。
> 2026-11-17 定稿，基于身份卡 v1.3.0 + dsh-file-vault v0.1 的实现。

## 1. 要解决的问题

长期会话里，规则、样本、模板、工具说明越堆越多，模型抓不住重点，不同任务的规范互相打架。手工维护的索引会漂移，越用越不可信。

目标不是「多记一点」，是**只记必要的，其余按需取**。

## 2. 核心抽象：资源

**身份卡维护的不是文件，是资源。** 资源包括：

| 类型 | 例子 | 载体 |
|---|---|---|
| 文件 | 实验报告、课件、代码 | 磁盘 |
| 契约 | 全局 7 条、卡的硬约束 | 卡正文 |
| 约束 | 验收判据、禁止项 | 卡正文 |
| 工具 | 被调用的能力 | 工具 schema |
| 技能 | 可复用的流程 | 卡 / 文档 |

身份卡本身不持有内容，只持有「引用 + 加载时机」。内容放在 vault，由路径、ID 或摘要定位。

## 3. 分层加载

```
L0 硬约束     每轮，几十字：不能做的事、必须做的事
L1 身份目录   每轮，一行一卡：id + 适用 + 不适用
L1' 工具目录  每轮，一行一工具：名字 + 一句话
L2 卡骨架     认领后：目标 + 硬约束 + 流程
L3 资源全文   按需：find → show
```

约束：**卡全文注入后撤不回来**，所以 L2 的裁剪必须发生在「卡怎么切分」这一步，不能指望运行时卸载。

## 4. 当前体积（2026-11-17 audit）

| 层 | 体积 |
|---|---|
| sections + contexts（卡目录、契约、人格） | 4,239 字 |
| 工具 schema（30 个工具） | 12,971 字 |
| 身份卡自身 | 1,355 字 |
| vault | 4,006 文件，查询进程内 p50 0.9 ms |

**结论：最大的优化对象是工具 schema，不是卡片目录。** 30 个工具里 render_architecture 822 字、bilij_reply 790 字、identity 534 字，bilij 一套 9 个工具占两千多字。

## 5. 设计原则（硬）

1. **兼容性优先**：只依赖插件协议（`name` / `inject` / `apply` 的 `systemPrompt` 与 `tools`）和 Node 内置模块。不依赖宿主预留特性、不依赖某个内部组件的行为。
2. **动态加载是加速层，不是地基**。没有它，功能退化为「常驻但描述更短」，不能不可用。
3. **可扩展**：新增资源类型不改核心；新增卡不改插件；新增工具不改卡。
4. **数据可重建**：`vault.db` 是缓存，`manifest.jsonl` 是真相，删库能从文件系统重建。
5. **单一真相**：资源路径只登记一处，其他位置存引用。
6. **注册的工具不依赖边缘组件特性**——这条优先于「省 token」。

## 6. 与 dsh-ops 的关系

借鉴机制，不采用实现：

| 借鉴 | 怎么用 |
|---|---|
| 渐进式披露 | L1 一行，L2 骨架，L3 全文 |
| 结果引用 | 大输出返回 ID，后续按 ID 取（vault 的 id + show 已是） |
| 动态工具加载 | 目标形态，但必须有不依赖宿主的退化方案 |
| 紧凑返回 / 紧凑错误 | 已用在 vault 的 find 输出（371 字符 ≈ 201 token） |

不采用：替换官方 read/glob/grep（侵入现有验证流程）、8 个 bundle 行（配置面过大）、窄版本声明（只兼容两个 rc 版本）。

**不装 dsh-ops 的理由**：它优化工具 I/O，我们的痛点是资源加载；它改动底层工具，和现有工作流冲突；收益（个位数百分比）不覆盖风险。

## 7. 待验证

- `tools_addition` 能否被第三方插件调用。若不能，退化方案三选一：
  - A. 一个 `toolbox` 元工具，按名字路由到内部能力（模型要学新调用方式）
  - B. 压缩 30 个工具的 description 到一行（不增加能力，只减字）
  - C. 按卡分批注册（需要运行时增删工具的能力）
- 判断标准：退化方案必须只依赖插件协议，不能为省 token 引入宿主私有接口。

## 8. 优化方向（按收益排序）

1. **工具 schema 12,971 字** —— 最大头，目标砍到 3,000 以内。
2. **契约分层** —— 硬约束（不可违反的 3 条）常驻，其余 4 条进 vault 做成可查资源。
3. **卡切片** —— 样本、验收清单、重建命令移进 vault，卡里只留一句「按需查」。
4. **vault df 表** —— 可选。当前 50k 文件 p95 37.8 ms，5 万规模可接受，不为不存在的规模做优化。

## 9. 决策记录

| 日期 | 决策 | 理由 |
|---|---|---|
| 2026-11-17 | vault 定位为身份卡的资源后端，不是独立检索项目 | 资源包含文件、契约、约束；检索只是取资源的动作 |
| 2026-11-17 | 不装 dsh-ops | 优化层不同，侵入性强 |
| 2026-11-17 | 动态加载不得依赖 `tools_addition` 作为唯一路径 | 兼容性与可扩展性优先 |
| 2026-11-17 | 卡全文一次注入，不做运行时卸载 | DSH 会话机制限制 |
| 2026-11-17 | vault 用 SQLite（node:sqlite），不用 FTS5 trigram | 中文两字查询 trigram 命中 0 条，改 bigram 倒排 |

## 10. 现状与边界

已实现：

- 身份卡 v1.3.0：目录注入、认领、互斥、切换、资源引用、clean、library、handoff。
- vault：注册、增量、find、show、verify、export/import、摘要（文本 + docx/pptx/xlsx）、排除规则、refresh。
- 接线：`identity library mode=find` 转发 vault，失败回退 markdown。

未做：

- 工具动态加载（待验证）。
- 卡切片（L2 瘦身）。
- 契约分层。
- 技能作为资源（形态未定）。
