## 关键发现

- **工具可以运行时增删**，`tools.register()` 返回 disposer，注销即生效，不需要宿主预留接口。
- **注册后 schema 立即变**，但调用通道要下一轮才可用。
- **注册是插件级的**，全局会话共享；按会话裁剪需要 `agent.ctx`。
- **宿主支持两套原生机制**：`assemble({ scope })` 的 scoped layers，以及工具 schema 的 `deferLoading` 字段。
- 插件「per-agent override」的官方做法：在该 agent 的 `agent.ctx` 里注册。

## 已确认的机制（2026-11-17）

按会话裁剪工具是宿主原生能力，不需要路由层，也不需要 `tools_addition`。证据链：

| 文件 | 事实 |
|---|---|
| `dsh-agent` | `agent/created` / `agent/disposed` 事件；参数是 `{ agent, source, signal }`（不是 agent 本身） |
| `dsh-system-prompt` | `section()` / `tools(provider)` 都走 `layers.effect(this.ctx, …)`，注释写明「for a per-agent override, register through that agent's `agent.ctx`」 |
| `dsh-tools` | `view(scope)` 按 scope 给可见工具集，`wireSchemas(scope)` 用它生成 schema；`presentAs()` 明确要求 scoped context（`agent.ctx`） |
| `dsh-tools` | `get(name, agent)` / `resolveExecution(name, agent, …)` 按 agent 解析 |
| `dsh-tools` | `view(scope)` 里有 `layer.admits(name)`，支持按层限制继承来的工具 |

**实验验证（2026-11-17）**：在 `agent/created` 里用 `agent.ctx.get('tools').register()` 注册 `scoped_ping`，实测——

- `agent.ctx.get('tools')` 可用，`agent.ctx.effect` 可用。
- 两个会话各注册一份同名工具，**不冲突**（日志两条 `registered function`，无 error）。
- 新会话里可调用。

**但有一个硬限制**：工具绑定在 agent 创建时确定，**已存在的会话不会刷新**。动态注册只对新建会话生效，对恢复的会话无效。所以「切卡时动态换工具集」在长期单会话里不成立。

`deferLoading` 确认是工具定义上的字段，`schemaOf` 会透传到 schema。**但 LLM 层是否据此裁剪提示词还没验证**——如果它只是标记，就不省 token。

## 工具层探索结论（2026-11-17 收尾）

三条路全试过：

| 方案 | 结论 | 依据 |
|---|---|---|
| 动态注册（`agent.ctx`） | 可行，但只对新会话生效 | `scoped_ping` 实验：两会话各注册一份不冲突，新会话可调，恢复的会话不刷新 |
| `deferLoading` | 字段存在，未找到裁剪逻辑 | `dsh-tools.schemaOf()` 透传完整 parameters；`system-prompt.assemble()` 原样保留 |
| 按 scope 隐藏他人工具（`admits`） | 宿主内部机制，无公开 API | `dsh-scope` 的 `ScopedLayers` 只暴露 peek/chainLayers/merge/effect |

根因：插件只能控制自己注册的工具。12,971 字 schema 里 identity 只占 777（identity 534 + powerful_clean 243），其余来自第三方插件。

## 新路线：`system-prompt/assemble` 过滤（2026-11-17）

比包装插件简单一个数量级，且没有双端插件的坑。

**依据**：`dsh-system-prompt` 的 `assemble()` 末尾是：

```js
const transformed = await this.ctx.waterfall(scopeTarget(this, scope), "system-prompt/assemble", assembly, context, () => Promise.resolve(assembly))
return transformed
```

`assembly` 的结构是 `{ sections, contexts, tools, variables }`，`tools` 也在里面，且 waterfall 返回值权威。

**校验不会拦**：

```js
function orderTools(tools, toolOrder, knownNames) {
  if (toolOrder === void 0) return tools.sort(compareToolNames)
  const unknown = toolOrder.filter(n => n !== "<unlisted-tools>" && !knownNames.has(n))
  if (unknown.length > 0) throw ...
}
```

- `toolOrder` 默认 `undefined`，只排序不校验内容。
- 配置了也只校验「配置里的名字是否已知」，不检查 tools 数组少了谁。
- `orderTools` 在 waterfall 之前执行，waterfall 之后没有二次校验。

**三个待验证点**：

| 检查项 | 状态 |
|---|---|
| waterfall 监听器的注册签名（`ctx.on` + `next` 的用法） | **已验证**：`argv=3`，签名 `(assembly, context, next)` |
| 裁掉 schema 后模型是否还能调（registry 里工具仍在，`resolveExecution` 能找到） | 推断可行，未实测 |
| runtime context 的 order 与 tools 的相对位置（决定前缀缓存是否本来就没命中） | 未验证 |

**风险**：模型看不到参数说明会瞎猜，必须同时提供一个索引工具（目录 + 参数查询入口）。

### tool_admin 与运行时加回（2026-11-18）

新增固定工具 `tool_admin`，不受白名单影响（在 `KEEP_ALWAYS` 里）：

| action | 行为 | 持久性 |
|---|---|---|
| `list` | 列出全部工具，分可见 / 持久 / 临时 / 被裁 | — |
| `enable` | 临时加回，写内存 `runtimeGranted` | 重启失效 |
| `always` | 持久加回，写 `~/.dsh/tool-grants.json` | 跨重启有效 |
| `forget` | 从持久和临时里一起移除 | — |

持久文件结构：`{ "always": ["工具名", …] }`，几十字节，启动时读一次。

工具描述里写明：身份卡缺工具时先告诉用户缺哪个、要临时还是持久，用户同意后再执行。

同时清理了 `dsh-tool-router`：从 profile 的 `dependencies` 和 `bundles` 移除，桌面目录保留（不再被加载）。

### clean 四档重写（2026-11-18）

中间文件命名规范改成 `_tmp_<类>_名字`，四类——`session`（会话依赖）、`enginee`（可复用工程文件）、`transport`（转换工具与中间态）、`record`（转换产物，成果）。

clean 四档：

| 档 | 入口 | 行为 |
|---|---|---|
| `tmp`（默认） | 扫 `_tmp_<类>_*` | 四类分组：session / transport 问「确定删除」，enginee 只列不删，record 正向问「确定不作为知识资产保留」 |
| `name` | `item` + `scope` | 点名删除，范围由 scope 指定或推断 |
| `list` | `items` + `scope` | 指定清单，无视命名 |
| `force` | `item` | 强删单个；失败只报告占用，不自动杀进程 |

同步移除 `powerful_clean`；旧 `_` 前缀不再当中间件，clean 只提示「另有 N 个未标注条目」。selftest 重写为四档覆盖，全过。

## skill 不是工具按需加载（2026-11-17 补充）

读了 `dsh-skill` 的实现：它只暴露「名字 + 摘要」，模型调 `skill` 工具时才给全文。`SkillLayer` 里没有 tools，所以 skill 管的是**指令体积**，不是工具 schema 体积。要用 skill 省工具定义，得配合路由：工具 schema 压成一个路由，用法说明写成 skill 按需加载。
