# 现有卡改造与资源漂移维护

两件事：五张卡按归藏项目的实体设计怎么改；资源外置后的漂移怎么用「查表 / 扫盘 / 推更新表」压住。状态：方案，未执行。

## 一、从归藏借的五条，落到五张卡

借的是设计不是功能：实体带时间、实体带动作、序列、引用不复制、索引是派生物。

| 卡 | 现在的问题 | 改造成 | 借的哪条 |
|---|---|---|---|
| `lab-report` | 第 5 节四条绝对路径（`D:\c_code\computer_graph\...`）；没有期次概念 | 资源化 + `series/` 按期记录 | works / column |
| `code` | 三条样本路径写死；收尾没有出口 | 资源化 + `handoff: [review]` | nextOfWork |
| `meta` | 样本节是「待填」，永远填不上 | 一份外置样本（一段对话的前后对比） | 样本外置 |
| `review` | 只写了怎么审，没写审什么 | `handoff` 接收端 + 检查表资源 | recipe 的步骤输入 |
| `ops` | ledger 是自由格式表格，各文件列不一致 | 条目字段对齐 works：id / 日期 / 文件 / 下一步 / 状态 | works 字段 |

五张卡统一加 `updatedAt`（front-matter），`audit` 报最久没动的三张。这是唯一一条机械改动。

## 二、资源的真相与派生

- **真相**：卡 front-matter 里的 `resources`，以及被引用的文件本身。
- **派生**：`@shared/resources/index.md`，一条资源一行：`引用 | 解析后路径 | mtime | size | sha8 | 上次校验`。
- 表可以随时删掉重建（扫卡里的 `resources` 字段），不进 git 也没关系。

规则只有一条：**表永远可以被丢弃，卡不能被表反向覆盖**。

## 三、漂移的三级处理

| 级 | 动作 | 时机 | 开销 |
|---|---|---|---|
| 查表 | 加载卡时只读表，不 stat 磁盘 | 每次认领 | O(1)，一次文件读 |
| 扫盘 | 按卡里的引用逐条 stat，重建表 | 显式命令 / 距上次超过 14 天 | O(引用数)，几十次 stat |
| 推表 | 差异不自动改卡，写进更新表 | 扫盘之后 | 0 |

「扫盘」在这里不遍历目录——只 stat 已知路径。遍历才是贵的，stat 四十次是毫秒级。所以重要的资源尽管扫，成本上不是问题，问题只在「多久扫一次」。

差异分三类，处理方式不同：

| 差异 | 判据 | 处理 |
|---|---|---|
| 断链 | 路径不存在 | 直接进更新表，标红；加载时提示「N 条引用缺失」 |
| 内容变 | sha8 不同、路径还在 | 进更新表，不自动改卡——模板变了可能意味着判据要跟着改 |
| 路径变 | 同名文件在新位置 | 只提示，等人确认；不做模糊匹配，猜错比不猜贵 |

## 四、重要和不重要怎么分

不是按「我觉得重要」，按**这条引用失效时会怎样**：

- 每次用卡都会读的（格式模板、检查表）→ 加载时显示状态，每周扫。
- 偶尔核对的（正例、反例、规则源）→ 只进更新表，等维护。
- 已经归档的（series 里的旧产物）→ 不扫，链接坏了也无所谓。

这个分法可以写进卡里：`resources` 的值带一个可选后缀 `?tier=hot|cold`，缺省 `cold`。hot 进表的头部并参与每周扫，cold 只排队。

## 五、谁来维护

你提的「助手卡有空时维护」是对的，但「有空」不能是触发条件。落到 `ops` 卡加一节职责：

- **触发**：更新表累计 ≥ 阈值（现在 28 条），或距上次扫盘 > 14 天，或使用者点名。
- **动作**：`identity resources scan` → 断链的问使用者；内容变的更新记录；路径变的改卡。**只改路径和标记，不许改判据**。
- **产出**：更新表清零，表里的「上次校验」刷新。
- **判据**：扫完 `identity resources status` 断链 0 条、超期条目 0 条。

先写进 `ops`，不新开卡。真到了每周都要维护的程度，再拆一张专职的。

## 六、两个必须防的失败

**更新表积液**。28 条已经积了，再往里推漂移会变成垃圾场。加一条硬规则：超过阈值时，每次加载卡在目录后面追加一行「更新表 N 条待处理」。不是阻断，是让它可见。

**表比卡新**。维护时只改表不改卡，下次重建表就白做。所以扫描器要先比对「表里的引用」和「卡里的引用」，两者不一致时以卡为准，并提示。

## 七、执行顺序

1. `ops` 卡加维护职责，`audit` 加老化统计（两处小改，顺带把 `updatedAt` 铺开）。
2. 实现 `resources scan` 与 `status`，先只支持 `private:` 和 `shared:`。
3. `lab-report` 做第一张改造卡（格式条款外置），验证表与扫盘跑通。
4. 其余四张照同一套改，`review` 最后——它依赖 `handoff` 先落地。

## 八、判据

- 断链 1 条时，`list` 显示 `↳ 5 个引用，4 个可解析`，卡照常加载，更新表多一条。
- 删掉索引表，`resources scan` 能从卡重建出同样的表（条数与路径一致）。
- 加载耗时与改造前差 5 ms 以内（表读一次）。
- 维护一轮后，更新表的漂移条目清零，`status` 断链为 0。
